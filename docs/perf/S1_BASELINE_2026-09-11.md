Kopi Senja (`qa+id`), Kemang table 12, `order.fluxyos.com`. Produced by
`npm run perf:s1`; the raw output of the final run is
`perf/out/s1-2026-09-10T19-02-39/` (gitignored). Plan:

## Findings, ranked

### F1 — Critical · one diner scrolling the menu blocks their own order

All five QR endpoints count against **the same per-IP document per minute**
(`ipKey(ip)` with no endpoint prefix, `netlify/functions/lib/rate-limit.js:61`),
but each compares that shared count with its **own** limit: photos 300, status
90, menu 60, **order 20, bill 20**. Photos fill the shared counter, and ordering
then refuses everyone on that IP until the minute rolls over.

- **Reproduced 4 of 4 times at zero load:** after scrolling the menu (60 photo
  requests), the diner's first order came back `429`. The page showed *"Could
  not send your order. Try again."* — the 429 body is plain text, so the page
  cannot tell it from any other failure.
- k6 smoke (3 phones, one IP): **3 of 3 orders refused.**
- **It has already happened in production:** the (never-expiring) `rate_limits`
  collection holds 8 IP-minutes over 20 between 7 and 9 September, across 5
  IPs — any order or bill request from those IPs in those minutes was refused.
- Every restaurant's wifi is one IP; Indonesian mobile carriers use CGNAT.

**Fix:** key each endpoint's IP bucket separately (`ip_order_<hash>`,
`ip_img_<hash>`…), so browsing can never spend the order allowance; return a
JSON `{error:'rate_limited'}` body so the page can say "wait a few seconds".
Retest: S7 and S1 (first order accepted).

### F2 — High · the functions run in Ohio; the database is in Singapore

All four Netlify sites report `functions_region: us-east-2`; Firestore is
`asia-southeast1`; the diners are in Jakarta and Singapore. Every Firestore
round trip from a function crosses the Pacific twice.

| Measured | |
|---|---|
| One Firestore read, Jakarta → Singapore (direct) | 38–76 ms |
| A function request that touches no database (OPTIONS) | 0.7–1.0 s to first byte |
| Two limiter transactions + one read, via the function | +0.9–1.1 s (~200 ms per operation) |
| The till's own writes (browser → Firestore) | **113–136 ms** |
| The diner's order write (browser → function → Firestore) | **3,400–7,600 ms** |

`qr-menu` makes about ten sequential Firestore operations, `qr-order` more
(three transactions). That is where the 2.9 s menu and the 4–7.6 s order go.

**Fix:** move the functions to `ap-southeast-1` (Singapore) — a Netlify site
setting, not a code change; check the plan allows choosing a region. Then
collapse the sequential reads (the two limiter transactions can run in
parallel, as `qr-menu-image` already does). Retest: S1; expect `qr-menu` under
500 ms.

### F3 — High · thumbnails are downloaded at 1280 px

On mobile 4G the first photo is painted at **8.2 s**, of which **5.0 s** is the
Cloud Storage download: the first screen requests 15 photos (the hero rail plus
cards under the name gate), all 1280 px WebP, **1.24 MB** competing for a
1.6 Mbps link. The cards display at ~100 px and the hero at ~400 px. Scrolling
the full menu costs **4.5 MB** of photos.

**Fix:** a small rendition (≈320 px, ~10 KB) for cards and the rail, the
1280 px original only in the item sheet; and hold card images until the name
gate is passed. Retest: S1 cold mobile; expect first photo under 3 s.

### F4 — High · four phones at one table take 8 seconds to order

k6 S4 smoke: four phones submitting within the same second, twice — every order
accepted and correct, but `qr-order` p95 **8.2 s**. Each request runs
transactions on the same shared IP limiter document and the same order
document, and contention retries across a 200 ms round trip compound. F1's fix
(separate buckets) and F2's (a nearby region) both shrink this.

### F5 — Medium · the till re-reads its outlet on every change

Measured: one refresh per listener delivery (6 for 6), two in flight at once,
**425 documents per refresh** on this workspace (the `items` collection is read
twice per refresh — `getPosOverview` and `refresh()` both call `getPosMenu`) and
**~1,660 on a mature outlet**. Refreshes take 250–330 ms, so the till itself
feels fine; the cost is reads. Confirms plan hypothesis H2; S3 measures it
under load.

### F6 — Low · smaller items

- CLS 0.161 on cold load (budget 0.1).
- Photo 302s are cached at Netlify's edge **per table URL**: the first diner at
  each table pays ~1.1 s per photo hop, later ones ~60–90 ms.
- `rate_limits` still has no TTL policy (`gcloud firestore fields ttls list`
  → 0); 564 expired documents present.

## What was not measured here

Load (S2–S11), payment (`payPosTableBill` — the cashier simulator voids
instead), and anything on a real phone. The S1 run is repeatable:
`npm run perf:s1`.
