## ⚠️ The 90-minute lunch rush (S3) is not a valid latency measurement

The load machine went to **idle sleep three minutes into the run** (03:26 WIB)
and was asleep for most of it — awake 03:23–03:26, 03:50–04:01, 04:08–04:14
(`pmset -g log`). Every wake released a queue of paused diners at once, and the
timeouts in the log are reconnect artifacts. **Its latency figures are not
reported anywhere.** Run load under `caffeinate -i` (now in the plan's run
commands) and re-run S3.

## S4 — four phones, one table (after the fix)

16 orders, four at a time, with the cashier sending the ticket to the kitchen
mid-burst.

| | Before (`3251146`) | After (`327e2df`) |
|---|---|---|
| `qr-order` p95 | 8,169 ms | **5,610 ms** |
| `qr-order` median | 4,047 ms | 3,630 ms |
| Integrity | ✓ | ✓ every accepted line exact |

Still slow: four appends to ONE order document contend in its transaction, and
every retry costs a round trip across the Pacific.

**New finding F7 — the kitchen race.** 5 of 16 rounds were refused
`order_closed`: the diner's round was read as appendable, then the cashier sent
the ticket to the kitchen before the append committed. The page then shows
*"This table was just settled. Ask staff to start a new order."* — false and
alarming; the table is mid-meal. By the rule the model already follows (the
kitchen is the boundary), such a round should open a NEW ticket, exactly as it
does when the kitchen took the ticket a moment earlier. Pre-existing — the same
check stood before the rework. Rare at a real table (a sub-second window), but
real.

## S10 — dropped responses (after the fix)

10 orders, 5 of them with the first response dropped after 150 ms while the
server carried on, then retried with the same `client_ref`.

| | Result |
|---|---|
| Retries answered with the SAME order | **5 of 5** |
| Orders written twice | 0 |
| Orders written without an accepted response ("ghosts") | 0 |

The idempotency record now lives inside the order transaction, which is what
closes this (see `docs/data-model/pos.md` §5a).
