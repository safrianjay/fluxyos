Still slow: four appends to ONE order document contend in its transaction, and
every retry costs a round trip across the Pacific.

**New finding F7 — the kitchen race.** 5 of 16 rounds were refused
`order_closed`: the diner's round was read as appendable, then the cashier sent
the ticket to the kitchen before the append committed. The page then shows
*"This table was just settled. Ask staff to start a new order."* — false and
alarming; the table is mid-meal. By the rule the model already follows (the
kitchen is the boundary), such a round should open a NEW ticket, exactly as it
does when the kitchen took the ticket a moment earlier. Pre-existing — the same
check stood before the rework. Rare at a real table (a sub-second window), but
real.

## The first photo on 4G (`order.html`, 17:30–19:00 WIB)

The last two budgets that failed were on the phone, not the server. The
waterfall (`perf/waterfall.js`, production, Lighthouse 4G) showed why:

- **The menu request left at 2.1 s for a 0.35 s answer.** It was the last line
  of a 3,500-line page script, and that script could not run until the whole
  80 KB page AND the Google Fonts stylesheet had arrived — a parser-inserted
  stylesheet holds back every script after it, and that one comes from a new
  origin (869 → 2,088 ms).
- **Then 22 downloads started at once**: three full-size hero slides, fifteen
  card photos, the font and the welcome art. The hero (71 KB) took 2.8 s. Its
  `fetchpriority="high"` did not help — downloads in flight together share a
  slow link roughly equally. None of the fifteen cards were on screen: the
  first sits at 801 px of an 839 px viewport, under the welcome sheet.

What changed in `order.html`:

1. A boot script at the top of `<head>` asks for the menu with the page's
   first packet and injects the fonts stylesheet (injected = blocks nothing).
   The page script takes over the same request.
2. The boot script asks for the hero's first slide the moment the menu lands,
   before the rest of the page has downloaded — from the 640px copy (~12 KB).
   The page swaps in the full photo once it has loaded, in a detached image,
   so a failed upgrade never costs a slide.
3. Every other photo — the other slides, every card — is parked in
   `data-held-src` until the first slide is in at full size, the diner
   scrolls/taps/types, or 4 s pass.

Measured before shipping, against production's API, fonts and storage, with
the page served from the checkout and its first byte held back 750 ms the way
production's is (`perf/serve-order.js`), median of 5:

| | First photo | LCP | Page script ready | Bytes to first screen |
|---|---|---|---|---|
| Before (HEAD) | 3,149 ms | 4,480 ms | 1,352 ms | 624 KB |
| + menu from `<head>`, fonts injected, hero first | 2,247 ms | 2,272 ms | 1,496 ms | 482 KB |
| + the first slide from its 640px copy | **1,975 ms** | **2,004 ms** | 1,506 ms | 399 KB |
| (not shipped) + comments stripped from the page | 1,983 ms | 1,996 ms | 1,139 ms | 344 KB |

**Why the page was not slimmed.** Stripping the comments takes the page from
~80 KB to ~38 KB on the wire and gets the page script running 0.37 s sooner —
the menu and the name form appear sooner — but it no longer moves the first
photo or LCP: those now wait on the photo's own two hops (the 302, then
storage), not on the page. It would mean a build step rewriting the one page
diners see, so production would run a file the tests never did. Worth doing
only if "menu on screen" gets a budget of its own.
